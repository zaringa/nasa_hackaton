# nasa_hackaton
**Для такого MVP я бы сделал алгоритм из двух частей: один раз рассчитываем, как рельеф закрывает небо в точке аппарата, затем для каждого момента времени проверяем положение Солнца и Земли относительно этого горизонта.**

Фиксированная высота здесь сильно помогает: пока координаты и высота аппарата не меняются, рельеф повторно считать не требуется.

Ниже — конкретная математическая модель и порядок реализации. Будем считать, что аппарат неподвижен относительно поверхности Луны, а его высота \(h\) задана **над грунтом в выбранной точке**. Для Солнца рассчитываем прямое освещение, для Земли — геометрическую видимость. Землю также можно использовать для проверки солнечных затмений.

## Что подаём на вход

Минимальный набор:

- Широта и долгота площадки.
- Постоянная высота расчётной точки аппарата над грунтом.
- Начало и конец периода в UTC.
- Модель рельефа.
- Параметры численного расчёта: пространственная детализация и шаг времени.

Для начала панель и антенну можно считать расположенными в одной расчётной точке. Позже для них легко задать разные высоты.

На выходе нужны временные ряды положения Солнца и Земли, доля открытого солнечного диска, интервалы освещения и видимости Земли, продолжительность непрерывных перерывов.

**Под «учесть весь рельеф» здесь следует понимать весь влияющий рельеф, представленный в выбранной модели высот.** Более мелкие особенности, которых в исходных данных нет, алгоритм восстановить не сможет.

## Какие данные и библиотеки использовать

Для этого вычислительного ядра я бы выбрал:

- **SpiceyPy** — положения Солнца и Земли, ориентация Луны.
- **NumPy** — векторная геометрия.
- **Rasterio** — чтение модели высот.
- **pyproj** — преобразования координат с лунной системой отсчёта.
- **SciPy** — уточнение времени пересечений горизонта.

Рельеф можно брать из **NASA LOLA**: доступны GeoTIFF отдельных южнополярных участков с сеткой 5 м/пиксель и данные более широких областей. У этих продуктов указаны система координат, разрешение и, для ряда наборов, ошибки высот. [pgda.gsfc.nasa.gov](https://pgda.gsfc.nasa.gov/products/78?utm_source=chatgpt.com)

Здесь есть обязательное условие: **координаты площадки, рельеф и положения небесных тел должны быть в согласованной лунной системе координат**. Например, опубликованные полярные DEM могут использовать `MOON_ME` реализации DE421. В SPICE для неё существует определённый фрейм `MOON_ME_DE421`; его нужно обеспечивать соответствующими файлами данных. [pgda.gsfc.nasa.gov](https://pgda.gsfc.nasa.gov/products/90?utm_source=chatgpt.com)

Все расчёты ниже удобно вести в метрах, радианах и `float64`. На границе со SPICE нужно переводить метры в километры.

## Математическая модель аппарата и поверхности

Для MVP подходит модель: **сфера Луны плюс радиальная высота рельефа**.

Обозначим:

- \(R\) — опорный радиус, относительно которого заданы высоты DEM.
- \(z(\varphi,\lambda)\) — высота грунта из DEM.
- \(\varphi\) — планетоцентрическая широта.
- \(\lambda\) — восточная долгота.
- \(h\) — высота расчётной точки над грунтом.

В рассматриваемых полярных продуктах LOLA используется опорная сфера радиуса **1 737 400 м**. Но в коде радиус следует брать из описания конкретного набора данных. [Lunar Polar Illumination](https://pgda.gsfc.nasa.gov/products/69?utm_source=chatgpt.com)

Единичный вектор от центра Луны к точке:

\[
\mathbf u(\varphi,\lambda)=
\begin{pmatrix}
\cos\varphi\cos\lambda\\
\cos\varphi\sin\lambda\\
\sin\varphi
\end{pmatrix}
\]

Для площадки с координатами \((\varphi_0,\lambda_0)\) получаем высоту грунта:

\[
z_0=z(\varphi_0,\lambda_0)
\]

Расстояние аппарата от центра Луны:

\[
r_o=R+z_0+h
\]

Его трёхмерное положение:

\[
\boxed{\mathbf p=r_o\,\mathbf u(\varphi_0,\lambda_0)}
\]

Положение любой точки рельефа:

\[
\boxed{\mathbf q=(R+z(\varphi,\lambda))\,\mathbf u(\varphi,\lambda)}
\]

Таким образом, высота аппарата автоматически складывается с высотой местности.

Здесь \(h\) отсчитывается радиально — по направлению от центра Луны наружу. Это удобное определение для MVP. Если позднее понадобится высота вдоль наклонённой оси аппарата, вместо радиального смещения можно будет использовать заданный вектор.

## Как получить местные азимут и высоту

Для аппарата строим локальные направления: **восток, север, вверх**.

Восток:

\[
\mathbf e=
\begin{pmatrix}
-\sin\lambda_0\\
\cos\lambda_0\\
0
\end{pmatrix}
\]

Север:

\[
\mathbf n=
\begin{pmatrix}
-\sin\varphi_0\cos\lambda_0\\
-\sin\varphi_0\sin\lambda_0\\
\cos\varphi_0
\end{pmatrix}
\]

Вверх:

\[
\mathbf u=
\begin{pmatrix}
\cos\varphi_0\cos\lambda_0\\
\cos\varphi_0\sin\lambda_0\\
\sin\varphi_0
\end{pmatrix}
\]

Пусть \(\mathbf v\) — вектор **от аппарата к рассматриваемому объекту**. Его компоненты в местной системе:

\[
E=\mathbf v\cdot\mathbf e,\qquad
N=\mathbf v\cdot\mathbf n,\qquad
U=\mathbf v\cdot\mathbf u
\]

Тогда азимут:

\[
\boxed{a=\operatorname{atan2}(E,N)\pmod{2\pi}}
\]

А угловая высота над местной горизонтальной плоскостью:

\[
\boxed{
\varepsilon=
\operatorname{atan2}\left(U,\sqrt{E^2+N^2}\right)
}
\]

Эти формулы используются одинаково:

- Для точки рельефа: \(\mathbf v=\mathbf q-\mathbf p\).
- Для Солнца: вектор от аппарата к Солнцу.
- Для Земли: вектор от аппарата к Земле.

Азимут получается от севера через восток. На самом географическом полюсе направление севера неоднозначно, поэтому нужно выбрать опорный меридиан и одинаково использовать его во всех расчётах.

## Как свести окружающий рельеф к профилю горизонта

Тебе нужна функция:

\[
H(a)
\]

Она отвечает на вопрос:

**«До какой угловой высоты поверхность Луны закрывает небо в направлении \(a\)?»**

Для непрерывной модели поверхности:

\[
\boxed{
H(a)=
\max_{\text{рельеф в направлении }a}
\varepsilon_{\text{рельеф}}
}
\]

Например, в одном направлении горизонт может быть на \(+3^\circ\), а в другом — на \(-0{,}2^\circ\).

После этого проверка видимости точечного объекта становится очень простой:

\[
\boxed{\varepsilon_{\text{объекта}}>H(a_{\text{объекта}})}
\]

### Формула для обхода рельефа по направлениям

Удобно для каждого азимута двигаться от площадки вдоль поверхности по большому кругу.

Пусть \(\psi\) — угловое расстояние от площадки относительно центра Луны. Тогда радиальное направление на очередную точку:

\[
\mathbf u_{\psi,a}
=
\cos\psi\,\mathbf u
+
\sin\psi\left(\cos a\,\mathbf n+\sin a\,\mathbf e\right)
\]

Из этого вектора получаем широту и долготу, а затем читаем высоту \(z(\psi,a)\) из DEM.

Обозначим радиус точки поверхности:

\[
r(\psi,a)=R+z(\psi,a)
\]

Её угловая высота относительно аппарата:

\[
\boxed{
\beta(\psi,a)=
\operatorname{atan2}
\left(
r(\psi,a)\cos\psi-r_o,\;
r(\psi,a)\sin\psi
\right)
}
\]

А профиль горизонта:

\[
\boxed{H(a)=\max_{\psi}\beta(\psi,a)}
\]

**Эта формула уже учитывает кривизну Луны и высоту аппарата.** Дополнительную поправку на кривизну поверх неё добавлять не нужно.

### Отрицательный горизонт нужно сохранять

У наблюдателя над гладкой сферой горизонт находится ниже горизонтальной плоскости:

\[
\boxed{
H_{\text{сфера}}
=
-\arccos\left(\frac{R}{R+h}\right)
}
\]

Например, для \(h=2\) м и указанного радиуса Луны получается примерно:

\[
H_{\text{сфера}}\approx-0{,}087^\circ
\]

Поэтому операция вроде `horizon = max(horizon, 0)` создаст ошибку: она искусственно закроет часть видимого неба.

Эта же формула пригодится для проверки реализации.

## Насколько далеко нужно учитывать рельеф

**Фиксированный радиус вроде 5 или 20 км сам по себе ничего не гарантирует.** Высокая дальняя гора может влиять на горизонт, даже если ближайшая поверхность уже скрылась за кривизной Луны.

Для автоматического выбора достаточного охвата можно использовать геометрическую границу.

Пусть для всей принятой модели поверхности известны:

\[
R_{\min}\le R+z(\varphi,\lambda)\le R_{\max}
\]

Здесь:

- \(R_{\min}\) — радиус сферы, которая гарантированно целиком находится внутри Луны.
- \(R_{\max}\) — верхняя граница радиуса поверхности.
- \(r_o\) — радиус положения аппарата.

Тогда достаточный угловой радиус области:

\[
\boxed{
\psi_{\max}
=
\arccos\left(\frac{R_{\min}}{r_o}\right)
+
\arccos\left(\frac{R_{\min}}{R_{\max}}\right)
}
\]

Соответствующее расстояние по опорной сфере:

\[
\boxed{d_{\max}=R\,\psi_{\max}}
\]

Это самостоятельный геометрический вывод для нашей модели: более далёкие точки закрыты внутренней непрозрачной сферой \(R_{\min}\) и уже не могут поднять видимый горизонт.

**Границы \(R_{\min}\) и \(R_{\max}\) должны относиться ко всей модели, а не только к уже загруженному небольшому фрагменту.**

Также нельзя автоматически принять \(R_{\min}=R\): в DEM есть отрицательные высоты. Опорная сфера не обязательно целиком лежит внутри реальной поверхности.

Для понимания масштаба: в условной модели с гладкой базовой сферой, аппаратом на высоте 2 м и максимальной горой высотой 1 км достаточный радиус получается около **62 км**. Это иллюстрация формулы, а не рекомендация всегда брать 62 км.

Практически я бы организовал данные так: детальный рельеф возле площадки, данные дальнего окружения и проверка достаточности общего охвата.

## Как построить горизонт без пропуска узких гребней

Здесь находится главная вычислительная сложность.

Простой вариант — выбрать сетку азимутов, например через \(0{,}05^\circ\), и по каждому направлению рассчитать максимум высоты рельефа. Но такой шаг является **начальной настройкой**, а не гарантией достаточной точности.

Узкое препятствие шириной \(w\), находящееся на расстоянии \(d\), занимает примерно:

\[
\Delta a\approx\frac{w}{d}
\]

Угол здесь в радианах.

Например, объект шириной 20 м на расстоянии 20 км занимает около \(0{,}057^\circ\). Редкая сетка может пройти между такими особенностями.

Поэтому при реализации нужно учитывать следующее:

- Вдоль направления проходить пересекаемые ячейки DEM и учитывать принятую интерполяцию поверхности.
- Уточнять угловую сетку там, где горизонт резко меняется.
- Проверять результат при уменьшении пространственного шага.
- Корректно замыкать профиль между \(360^\circ\) и \(0^\circ\).
- Не заменять пропуски данных нулевой высотой.
- При уменьшении детализации дальнего рельефа сохранять информацию о высоких участках: усреднение может убрать вершину.

**Максимум только по центрам пикселей, округлённым до ближайшего азимута, может создавать ложные просветы.**

Если потребуется уверенно проверять конкретные лучи относительно выбранной поверхности, можно построить треугольную сетку DEM и искать пересечения лучей с ней. Тогда не возникает дополнительного пропуска из-за сетки азимутов. В SPICE для моделей поверхности и пересечений лучей предусмотрен механизм DSK. [naif.jpl.nasa.gov](https://naif.jpl.nasa.gov/pub/naif/toolkit_docs/C/req/dsk.html?utm_source=chatgpt.com)

Для первого прототипа профиль горизонта удобнее по скорости и для объяснения результатов. Его точность нужно контролировать отдельно от точности эфемерид.

## Как получать положение Солнца и Земли

Для автоматического локального расчёта здесь хорошо подходит `spiceypy.spkcpo`.

Функция вычисляет положение цели относительно наблюдателя с постоянными координатами в заданной системе. Это соответствует аппарату, закреплённому на поверхности Луны. Она также позволяет использовать предусмотренные SPICE поправки на распространение света и аберрацию. [naif.jpl.nasa.gov](https://naif.jpl.nasa.gov/pub/naif/toolkit_docs/C/cspice/spkcpo_c.html?utm_source=chatgpt.com)

После загрузки согласованного набора SPICE kernels вызов может выглядеть так:

```python
import numpy as np
import spiceypy as spice


def body_vector_m(
    target: str,
    et: float,
    observer_m: np.ndarray,
    frame: str,
) -> np.ndarray:
    """Вектор от аппарата к телу в согласованной лунной системе."""
    state, _ = spice.spkcpo(
        target=target,
        et=et,
        outref=frame,
        refloc="OBSERVER",
        abcorr="CN+S",
        obspos=np.asarray(observer_m, dtype=np.float64) / 1000.0,
        obsctr="MOON",
        obsref=frame,
    )
    return np.asarray(state[:3]) * 1000.0
```

Использование:

```python
sun_vector = body_vector_m("SUN", et, observer_m, frame)
earth_vector = body_vector_m("EARTH", et, observer_m, frame)
```

Важные детали:

- `et` — время в шкале SPICE, полученное штатным преобразованием из UTC.
- `frame` — согласованный с координатами аппарата и DEM лунный фрейм.
- `observer_m` — положение аппарата относительно центра Луны.
- Возвращённый вектор уже направлен **от аппарата**: повторно вычитать его координаты не нужно.
- `CN+S` задаёт расчёт видимого направления с соответствующими поправками. [naif.jpl.nasa.gov](https://naif.jpl.nasa.gov/pub/naif/toolkit_docs/FORTRAN/spicelib/spkcpo.html?utm_source=chatgpt.com)

Либрация и изменение ориентации Луны должны получаться из этих исходных данных и преобразований.

## Как считать свет и видимость Земли

### Сначала реализуй проверку центра

Для Солнца:

\[
g_S(t)=\varepsilon_S(t)-H(a_S(t))
\]

Для Земли:

\[
g_E(t)=\varepsilon_E(t)-H(a_E(t))
\]

При положительном значении центр тела открыт, при отрицательном — закрыт.

Полезно сохранять само значение \(g\): это **угловой запас над горизонтом**. Он показывает, насколько результат близок к границе видимости.

Этого достаточно, чтобы проверить весь вычислительный конвейер. Для расчёта солнечного света следующим небольшим шагом стоит добавить размер диска.

### Солнце нужно представить диском

Угловой радиус Солнца:

\[
\boxed{
\rho_S(t)=
\arcsin\left(\frac{R_S}{\|\mathbf v_S(t)\|}\right)
}
\]

где \(R_S\) — физический радиус Солнца, а \(\mathbf v_S\) — вектор от аппарата к его центру.

Для неровного горизонта удобен численный метод:

- Распределить точки по площади видимого диска.
- Для каждой точки получить отдельное направление.
- Рассчитать её азимут и высоту.
- Проверить, закрывает ли это направление рельеф.
- Усреднить результат.

\[
\boxed{
f_S(t)\approx
\frac1N\sum_{j=1}^{N}
\mathbf 1\!\left[\varepsilon_j(t)>H(a_j(t))\right]
}
\]

Здесь \(f_S\) — доля открытого солнечного диска, а \(\mathbf 1\) равна единице, если условие выполнено.

Для начала можно использовать 256–1024 детерминированных точки, распределённых равномерно по площади, и увеличивать число точек возле частичного перекрытия до устойчивости результата. В этой модели яркость диска принимается равномерной.

**Каждая точка диска должна проверяться по своему азимуту.** Проверка верхнего края только относительно горизонта под центром Солнца может ошибаться на неровном гребне.

NASA также использует конечный размер диска при моделировании полярной освещённости. [Lunar Polar Illumination](https://pgda.gsfc.nasa.gov/products/69?utm_source=chatgpt.com)

### Учёт затмения Солнца Землёй

Поскольку положение Земли уже рассчитано, можно добавить её перекрытие солнечного диска.

Для минимальной геометрической модели представляем Землю непрозрачным шаром. Её угловой радиус:

\[
\rho_E=
\arcsin\left(\frac{R_E}{\|\mathbf v_E\|}\right)
\]

Пусть \(\hat{\mathbf s}_j\) — направление на выбранную точку солнечного диска, а \(\hat{\mathbf e}\) — направление на центр Земли.

Эта точка закрыта Землёй, если:

\[
\hat{\mathbf s}_j\cdot\hat{\mathbf e}
\ge \cos\rho_E
\]

Для системы Солнце — Земля — лунный наблюдатель Земля находится ближе Солнца, поэтому проверка имеет понятный геометрический смысл.

В результате каждая точка солнечного диска проходит **две проверки**: на перекрытие рельефом и на перекрытие Землёй. Открытые точки суммируются одной общей маской.

Это корректнее, чем независимо вычислить две доли видимости и перемножить их: рельеф и Земля могут перекрывать одну и ту же часть диска.

### Что выдавать для Земли

В минимальной версии достаточно:

```text
earth_center_visible
earth_clearance_deg
```

Позже тем же методом выборки точек можно добавить долю открытого земного диска.

Метрику следует называть именно геометрической видимостью. Видимый участок Земли ещё не означает видимость нужной наземной станции; NASA отдельно оговаривает это ограничение для оценок связи. [Lunar Polar Illumination](https://pgda.gsfc.nasa.gov/products/69?utm_source=chatgpt.com)

## Как автоматически находить временные окна

Теперь для любого момента \(t\) у тебя есть:

- Доля открытого солнечного диска \(f_S(t)\).
- Видимость центра Земли.
- Азимуты, высоты и запасы над горизонтом.

Дальше нужно извлечь непрерывные интервалы.

Для Земли ищем переходы функции:

\[
g_E(t)=\varepsilon_E(t)-H(a_E(t))
\]

Для солнечного эксплуатационного окна можно задать порог:

\[
g_S(t)=f_S(t)-f_{\min}
\]

Например, миссия может считать достаточным определённый процент открытого диска. Порог должен быть параметром сценария.

Практический порядок:

- Рассчитать предварительную временную сетку.
- Найти участки около границ видимости.
- Уточнить эти участки дополнительными вычислениями.
- Найти моменты переходов.
- Собрать интервалы и их длительности.

Для первоначального запуска можно взять шаг **5 минут**, затем уточнять переходы до выбранного допуска, например 30–60 секунд.

Но здесь есть важное ограничение: **два перехода внутри одного шага могут остаться незамеченными**. На обоих концах интервала будет одинаковое состояние, хотя внутри было короткое окно.

Поэтому нужно заранее определить минимальную длительность событий, которые ты хочешь обнаруживать. Если интересуют окна порядка десяти минут, шаг в час слишком велик. Возле сложных участков горизонта полезно дополнительно делить временные интервалы.

Для непрерывного \(g_E(t)\) можно применять бисекцию или `scipy.optimize.brentq` после обнаружения подходящего интервала. Для дискретной выборки солнечного диска доля \(f_S\) меняется ступенчато, поэтому её численную детализацию тоже нужно учитывать.

**Точность поиска корня и точность физического результата — разные вещи.** Ошибка рельефа может сдвигать событие гораздо сильнее, чем выбранный секундный допуск.

## Какие показатели рассчитывать автоматически

Из найденных интервалов:

- Суммарное время освещения по выбранному критерию.
- Самый длинный непрерывный тёмный период.
- Самый длинный непрерывный световой период.
- Время до ближайшего появления или исчезновения света.
- Суммарное время видимости Земли.
- Самый длинный перерыв видимости Земли.
- Пересечение световых окон и окон видимости Земли.

Дополнительно полезен показатель:

\[
T_{\text{экв}}=\int_{t_0}^{t_1}f_S(t)\,dt
\]

Он даёт эквивалентное время полного раскрытия солнечного диска в принятой модели. Это ещё не электрическая энергия: для неё нужны ориентация, площадь и эффективность панели.

При адаптивной сетке длительности нужно считать по реальному времени между событиями, а не через количество подходящих отсчётов.

Начальные и конечные окна могут быть обрезаны периодом анализа. Это стоит сохранять отдельными признаками.

## Как организовать вычислительное ядро

Я бы разделил его на несколько небольших модулей:

- `terrain.py` — чтение DEM, интерполяция, покрытие и пропуски.
- `geometry.py` — положение аппарата, локальный базис, азимут и высота.
- `horizon.py` — построение и кеширование горизонта.
- `ephemeris.py` — работа со SPICE.
- `visibility.py` — солнечный диск, Земля, затмения.
- `events.py` — временные интервалы и показатели.

Общий псевдокод:

```python
def analyze(site, period, settings):
    # Подготовка постоянной геометрии
    ground_height = terrain.height_at(site.lat, site.lon)
    observer, basis = make_observer(site, ground_height)

    horizon = load_or_build_horizon(
        observer=observer,
        basis=basis,
        terrain=terrain,
        settings=settings,
    )

    def evaluate(time):
        sun = ephemeris.vector_from_observer(
            "SUN", time, observer
        )
        earth = ephemeris.vector_from_observer(
            "EARTH", time, observer
        )

        return calculate_visibility(
            sun=sun,
            earth=earth,
            basis=basis,
            horizon=horizon,
            settings=settings,
        )

    # Расчёт периода и уточнение событий
    samples = sample_period(evaluate, period, settings)
    samples = refine_intervals(evaluate, samples, settings)
    windows = extract_windows(samples, settings)
    metrics = calculate_metrics(windows, samples)

    return samples, windows, metrics
```

Это схема организации, а не готовая реализация: наиболее содержательная часть находится внутри построения горизонта и уточнения событий.

Кеш горизонта должен зависеть от координат, высоты аппарата, версии DEM, системы координат и настроек пространственного расчёта. Дата в этот ключ не входит.

## Что проверить перед использованием реального рельефа

Сначала проверь геометрию на простых случаях.

**Гладкая сфера.** При постоянном DEM горизонт должен совпадать с:

\[
-\arccos\left(\frac R{R+h}\right)
\]

**Известное препятствие.** Добавь искусственный гребень в определённом направлении и проверь, что он закрывает источник на ожидаемой высоте.

**Переход через север.** Направления около \(359{,}99^\circ\) и \(0{,}01^\circ\) должны обрабатываться без искусственного разрыва.

**Изменение высоты.** При увеличении радиальной высоты аппарата профиль окружающего рельефа в фиксированном направлении не должен подниматься.

**Проверка небесных направлений.** Сравни азимуты и высоты с JPL Horizons при согласованных настройках.

**Проверка детализации.** Уменьши пространственный и временной шаги и сравни полученные окна. Отдельно проверь узкие препятствия и короткие периоды затенения.

Первый законченный вариант я бы довёл до одной функции `analyze(lat, lon, height_m, start_utc, end_utc)`, которая возвращает проверенный горизонт, временные ряды и интервалы. После этого автоматическое сравнение дат и площадок будет обычным повторным запуском расчёта с переиспользованием подготовленной геометрии.
